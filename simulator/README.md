# Simulator internals

This folder holds the exam simulator. See the [main README](../README.md) for a quick start; this page covers how it works and how to operate it.

## Topology

| VM | Role | Default RAM |
|---|---|---|
| `cka-base` | Exam terminal (ttyd on port 7681, forwarded to the Mac). Has no kubeconfig. | 1 GiB |
| `cka-cp1` | cluster1 control plane, Kubernetes v1.37 | 2.5 GiB |
| `cka-w1` | cluster1 worker | 2 GiB |
| `cka-cp2` | cluster2 control plane, v1.37 | 2 GiB |
| `cka-w2` | cluster2 worker, one minor version behind (upgrade tasks) | 1.5 GiB |

You can override the RAM sizes when creating the VMs, for example `MEM_CP1=3GiB ./cka up`. The VMs share Lima's `user-v2` network. Pods use Calico with VXLAN: cluster1 has pod CIDR `10.244.0.0/16` and service CIDR `10.96.0.0/12`; cluster2 has `10.48.0.0/16` and `10.112.0.0/16`.

Each task names a control plane host. Inside the VMs:

- The `candidate` user can `ssh` from `base` to every node and has passwordless `sudo`.
- `kubectl` is configured for `candidate` on both control plane nodes.
- Root can `ssh` from a control plane to its workers. Setup and check scripts use this.

## Commands

```bash
./cka up                 # create VMs + install both clusters (re-runnable)
./cka exam [--restart]   # start/open the portal on http://localhost:8888
./cka status             # VMs and nodes
./cka stop | start       # stop/start the VMs, state is kept
./cka ssh <vm>           # root shell (cka-base, cka-cp1, cka-w1, cka-cp2, cka-w2)
./cka destroy            # delete everything
```

## Exam flow

1. **Prepare** runs each selected task's `setup.sh` as root on its cluster. Setups are idempotent: every attempt starts from a clean scenario. Some tasks must be prepared before others on the same node; `setup_priority` controls the order.
2. **Start exam** starts the timer. At 0:00 the exam is submitted automatically.
3. During **section exams**, **Check** runs the current task's `check.sh` and lists each check as passed or failed. **Show solution** reveals `solution.md`. The mock exam has neither.
4. **End Exam** runs every `check.sh`. Each check of a task has equal weight within the task's points. Constraint checks (`guard`) only count once a real objective has passed, so doing nothing scores 0.
5. Results show the score per section or domain, every check, the explained solution and links to the related course lectures. Attempts are stored in `state/history.json`. The lobby uses them for the **Weak** mode and the list of lectures to review.

Lecture links use `https://www.udemy.com/...` by default; set `UDEMY_BASE=https://<company>.udemy.com` for Udemy Business.

## Folders

```
cka               orchestration CLI
lima/             VM templates (Ubuntu 24.04, vz, user-v2 network)
provision/        node.sh (containerd, kubeadm…), cp-init.sh (kubeadm init + Calico), addons.sh, base.sh
questions/        one folder per task + _lib.sh (helpers prepended to every script)
exams/            exam definitions; section exams are generated by dev/build-exams.py
portal/           server.py (stdlib HTTP server, grader) + static UI, curriculum.json (lecture ids)
dev/              qa.sh, qa-batch.sh, build-exams.py, reset-cluster2.sh
state/            runtime data: logs, ssh keys, exam state, history (not committed)
```

## Writing and verifying tasks

See [questions/README.md](questions/README.md) for the task format and rules. A task is only published after an end-to-end check:

```bash
dev/qa.sh <task-id> all      # setup → check (must fail) → reference solve → check (must pass)
dev/qa-batch.sh <ids...>     # several tasks one after another, cleaning up namespaces
```

Mark the task `"verified": true` in its `meta.json`, then regenerate the section exams:

```bash
python3 dev/build-exams.py 2 3 4 5     # sections to publish
```

## Troubleshooting

- **`Address already in use`** when starting the portal means it is already running. Use `./cka exam` to open it or `./cka exam --restart`.
- **The terminal pane is empty.** The VMs are probably stopped; run `./cka start`.
- **Pods are Pending with "Too many pods" on `cka-w1`.** Leftover namespaces from many attempts are filling the worker. Setups clean up after themselves, but `kubectl get ns` on `cka-cp1` shows any stale task namespaces you can delete.
- **cluster2 control plane is slow after apiserver edits.** kube-controller-manager and kube-scheduler exit when the apiserver restarts, and kubelet backs them off for up to 5 minutes. Tasks that edit the apiserver reset this in their setup. Run `dev/reset-cluster2.sh` to restore cluster2 completely.
